# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:
    - Кто: `system:serviceaccount:secure-ops:monitoring`
    - Где: неймспейс `kube-system`, ресурс `secrets`
    - Почему подозрительно: злоумышленник может пытаться получить доступ к списку секретов кластера, чтобы затем скомпрометировать их или использовать для изменения/удаления ресурсов

2. Привилегированные поды:
    - Кто: `system:serviceaccount:kube-system:daemon-set-controller`
    - Комментарий: создание привилегированного пода позволит выполнить действия, запрещенные политиками безопасности, что приведет к возможности модифицировать кластер

3. Использование kubectl exec в чужом поде:
    - Кто: `minikube-user`
    - Что делал: попытался получить доступ к `/etc/resolv.conf` кластера для получения информации о настройках DNS

4. Создание RoleBinding с правами cluster-admin:
    - Кто: `minikube-user`
    - К чему привело: `rolebinding.rbac.authorization.k8s.io/escalate-binding` created, т.е. успешно создался новый `RoleBinding` между сервисным аккаунтом `monitoring` и кластерной ролью `cluster-admin`

5. Удаление audit-policy.yaml:
    - Не найдено (команда в скрипте `simulate-incident.sh` завершилась ошибкой)

## Вывод

* Ввести явные роли для доступа к секретам и конфигурационным данным каждого неймспейса, и выдать доступ на чтение секретов только пользователям с этими ролями
* Ограничить создание privileged-подов в кластере. Для этого определить в кластере pod security policy, позволяющую создание в кластере только baseline либо restricted подов
* Пересмотреть права для пользователя minikube-user, ограничив его действия по принципу least privilege
